```yaml

kind: PodLoadTest
metadata:
  name: podloadtest-sample
spec:
  total: 5000
  maxInFlight: 4000
  submitRatePerSecond: 300
  submitBurst: 300
  createConcurrency: 50
  durationSeconds: 600
  podTimeoutSeconds: 120
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: tars-shanghai-registry-vpc.cn-shanghai.cr.aliyuncs.com/infra/busybox:20260914

        resources:
          requests:
            cpu: 10m
            memory: 16Mi
          limits:
            cpu: 100m
            memory: 64Mi

    deleteCompletedPods: true
    deletePVCs: true

```

Pod 运行时间固定为 10s（业务侧最快的真实模拟）。

## 5. 生命周期

| 指标 | 值 |
|---|---|
| `podloadtest_pod_lifetime_seconds` 平均 | 61.59s |
| p50 / p90 / p95 / p99 | ≤120s（均落在 60s–120s 桶） |

该指标统计的是「创建 → reclaimer 实际删除」，包含了回收队列积压，因此远大于 10s 业务运行时间。业务运行时间与回收延迟需要拆开看，后续优化会新增 `pod_completion_duration_seconds`。

## 6. 结论与瓶颈

1. **创建侧瓶颈是 Pod create API 延迟**：平均 1.414s、p95 ≤5s；50 并发下上限约 35 pods/s。节点资源（49 节点）不是瓶颈。
2. **回收侧瓶颈是单 worker**：约 19 pods/s，提交完成时积压 1746 个 Completed Pod，排空需要约 2 分钟。
3. **创建和回收互不阻塞**：创建全程 0 错误，回收积压期间创建继续，符合两个独立控制器的设计；但高 churn 场景下 reclaimer 吞吐不足。
4. **创建器自身有额外 API 开销**：每轮 reconcile 用 APIReader 全量 List in-flight Pod；4000 Pod 时列表很大，整轮仅约 59 次 reconcile。
5. **无 PVC 场景仍在尝试清理 PVC**：回收路径对每个 Pod 都会 Get 同名 PVC，增加 API 负载（本轮无 storage）。

## 7. 优化方向（下一轮）

- Reclaimer 设置 `MaxConcurrentReconciles`（20–50），提升删除吞吐。
- 创建器改用 manager cache 统计 in-flight，去掉每轮全量 APIReader List。
- 无 storage 时跳过 PVC 清理 Get。
- 新增 `pod_completion_duration_seconds`，区分业务运行时间与回收积压。
- 下一轮 `createConcurrency` 提升到 100，观察提交上限。
- 如需测集群极限，可在集群空闲时段复测，排除现有 Argo 工作负载对 API 延迟的影响。
